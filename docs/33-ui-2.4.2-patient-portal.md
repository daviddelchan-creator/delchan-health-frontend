# UI-2.4.4 - Patient Dashboard Real

This document covers the architectural and navigation setup for the Patient Portal, including the real dashboard implementation.

## Architecture
- The patient portal is fully isolated from the clinical workspace (`DelchanAppShell`) and lives under `app/patient/`.
- It uses a custom `PatientAppShell` wrapper utilizing standard Mantine 8 components.
- State is managed centrally by `PatientDashboardContext`, abstracting Medplum authentication away from the client-side UI and securely accessing FHIR resources via our unified `/api/patient/dashboard` endpoint.
- Server-Sent Events or active WebSockets are reserved for real-time states; basic navigation uses stateless URL-based route active states using Next.js `usePathname`.

## Navigation & AppShell Behaviour
- **Desktop:** Utilizes a standard left `AppShell.Navbar` with full labels.
- **Tablet:** Adapts navbar breakpoints and hides when necessary according to standard Mantine media queries (`breakpoint="sm"`).
- **Mobile:** Replaces the side Navbar with a persistent bottom `AppShell.Footer` utilizing accessible `UnstyledButton` elements for routing.
- **Active States:** Determined strictly via exact matching for the root route (`/patient` or `/patient/`) and explicit segment matching logic for nested routes (e.g. `pathname === '/patient/consultas' || pathname.startsWith('/patient/consultas/')`) to prevent false positive matches like `/patient/consultasXYZ`.
- **Icons:** Standardized using `@tabler/icons-react` to maintain consistency with the broader Delchan Health OS SaaS.

## State Management (UI)
The layout implements an explicit state machine for loading contexts:
- `INITIALIZING` / `LOADING` → Minimal loading view.
- `UNAUTHORIZED` → Graceful error state with retry.
- `FORBIDDEN` → Strict rejection for non-patient profiles trying to spoof or access the portal.

## UI-2.4.4 — Patient Dashboard Real
The dashboard (`/patient`) implements a clinical, human, and modern experience displaying real data from the backend.

### Data Source & Security
- Consumes real FHIR data strictly via `GET /api/patient/dashboard`.
- **Zero Client-Side Patient IDs:** The dashboard natively refuses `patientId` coming from the client payload (`?patientId=` or `body.patientId`). Identity is derived entirely from the server-side authorized Medplum token.
- No new FHIR operations or endpoints were created.

### Components & Visual Identity
- Utilizes exclusively native Mantine 8 tokens from `app/theme.ts` (e.g., `teal` color scheme) avoiding arbitrary hex codes.
- `Card`, `Stack`, `Grid`, `Group`, `ThemeIcon`, `Badge`, and `ActionIcon` used for a structured UI.
- All iconography migrated completely to `@tabler/icons-react`.

### Displayed Information
- **Greeting:** Extracts real given name from the Patient profile.
- **Next Appointment:** Deterministically filters for future, valid `booked` or `arrived` appointments, selecting the single closest date/time. Displays real date, time, description (falling back to "Consulta" strictly, without inventing clinical logic), and the related Practitioner via the participant list. Link to the actual `/patient/consultas` page. If empty, gracefully shows a "Tudo em dia" feedback.
- **Quick Actions:** Uses dynamic grid layout mapping real routes (`/patient/consultas`, `/patient/historico`, `/patient/documentos`, `/patient/saude`, `/patient/perfil`) wrapped in accessible semantic tags.
- **Clinical Summary:** Calculates and shows actual length metrics from the `data` collections for Documents, Medications, Diagnostics, and Observations, handling pluralization and empty states ("Nenhum documento", "1 medicamento", "2 documentos disponíveis").

### Limitations / Work-in-progress (Em breve)
- Internal page flows for specific appointments, documents views, health metrics detail, and profile editing remain "Em breve" and link to layout stubs to prevent 404 errors until their specific UI phases (e.g. UI-2.4.5, UI-2.4.6) are completed.

## Accessibility
- Mobile bottom navigation relies on `UnstyledButton` wrapping to provide proper DOM elements (`button` tag), `tabIndex`, visible focus outlines natively from Mantine, and descriptive `aria-label`s for screen readers.
- Focus traps and adequate semantic contrasting (`dimmed` vs `teal-filled`) maintain the active navigation state clearly without depending on color solely.
