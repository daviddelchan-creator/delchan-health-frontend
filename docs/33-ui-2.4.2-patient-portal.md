## Architecture

**Data Access Layer Location:** `app/patient/api/dashboard.ts` + `app/patient/state/usePatientDashboard.ts`
**Authentication Mechanism:** `useMedplum().getAccessToken()` retrieving token handled by Medplum Provider -> Header injected to `/api/patient/dashboard` where Server validates Medplum Session and `auth/me`.
**Patient Identity Source:** The server-side API guarantees the profile returned is inherently tied to the active token. No `patientId` parameter is sent from the UI.
**State Model:**
- `INITIALIZING` (Waiting for context)
- `LOADING` (Fetching Data)
- `READY` (Display Data)
- `EMPTY` (No Appointments/Documents)
- `ERROR` (Server/Fetch Error, sanitized securely to hide raw stack traces/PHI)
- `UNAUTHORIZED` (Missing or invalid token)
- `FORBIDDEN` (Token valid, but `resourceType !== 'Patient'`)

## Known Limitations
- The OCR processing, health connect endpoints, and detailed telemedicine capabilities are not attached to this portal UI yet.
- All sub-navigation routes currently display an explicit "Em breve" (`EmptyState`) rather than rendering actual modules or returning 404s.
- `Public Anamnese` (`/patient/[id]/anamnese`) continues functioning as a decoupled entity entirely independent of this authentication portal.
